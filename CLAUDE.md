# 3d-print-learning

**Дима даёт модель («хочу напечатать вот это», ссылка на MakerWorld, STL, деталь из Fusion) → скилл `print-model`.** Он ведёт от источника до нарезанного файла, открытого в Studio: пресеты, качество нарезки, прогноз, что нажать. Заправка нового пластика → его справочник `filament-calibration.md`. **Скилл приходит из публичного плагина `bambu-print-model`** (`~/dev/bambu-print-model`, GitHub `rudnik275/bambu-print-model`, ADR-0006): там знание и переносимые инструменты на английском, здесь — опыт (`prints/`, `lessons/`, ADR, `CONTEXT.md`) и личные надстройки из этого файла (клики в Studio, принтер по LAN, «запускай»). Урок из печати → правило в плагин (без дат и имён, с числами) при закрытии сессии; запись о печати остаётся здесь. Копии переносимых инструментов в `tools/` пока остаются ради `prints/*/build.py`; канонические версии — в плагине.

Дима учится печатать красиво на Bambu Lab A1 mini и моделировать под печать во Fusion. Агент здесь — **учитель за рулём**: объясняет «почему», а настройки Studio выставляет **сам** — собирает проект-3MF с нужными значениями (`tools/bbs_project.py`), открывает его в Studio и перечисляет, что изменил; Дима смотрит и жмёт Print. Инструкции вида «найди поле X и поставь Y» не давать — Дима их не находит, это выматывает (2026-09-16). Fusion: читать дизайн скриптами (`readOnly`) свободно; строить и менять модели — только по явной просьбе, Дима моделирует сам.

## Что фиксировать

В репо попадают **выводы**, не конспект. Разовые вопросы «как работает X» живут в чате.

- решение по профилю или процессу → `docs/adr/NNNN-<тема>.md`; если оно меняет то, как готовится любая модель, — продублировать правилом в скилл `print-model`
- итог урока → `lessons/NN-<тема>.md`: симптом → диагноз → что поменяли → результат
- проблемная или эталонная печать → `prints/YYYY-MM-DD-<name>/`: 3MF проекта, `settings-diff.txt` из `bbs_current.py`, фото, короткая заметка
- живой снимок железа, пластика, базовых пресетов и терминов → `CONTEXT.md`

Источник правды по железу и пластику — Obsidian `справочники/3d-печать.md` и `справочники/филаменты-инвентарь.md`; `CONTEXT.md` — снимок оттуда, сверять перед советом по пластику.

## Видеть Bambu Studio — файлами, без MCP

- `tools/bbs_current.py` — что открыто в Studio сейчас (её автосейв) или любой сохранённый `.3mf`: пресеты, стол, объекты, все отличия от базовых пресетов.
- `tools/bbs_project.py` — собрать полный проект из автосейва (`assemble`), сделать вариант с подмножеством объектов и изменёнными ключами (`variant --keep … --set key=value`), перенести чужой проект (MakerWorld, другой принтер) на наши принтер/филамент/процесс с сохранением авторских правок процесса (`retarget --machine … --process … --filament … --bed …`, урок 4); `tools/bbs_rebuild.py` — восстановить меши из исходных экспортов Fusion, когда автосейв уже ротировался. Ключевая ловушка: при загрузке 3MF Studio сбрасывает на текущий системный пресет все ключи, не перечисленные в `different_settings_to_system` (список по вкладкам process;filament;machine) — `variant` заполняет его сам; без него изменение молча пропадает (2026-09-16). Проверка — CLI-нарезка (`--slice 0 --export-3mf`). Отдать в печать — `gcode3mf` (CLI-экспорт → файл без геометрии, который Studio открывает как нарезанный: Preview + активная Print plate) и `open -a BambuStudio file.gcode.3mf` в **уже запущенную** Studio; `app.single_instance = true` в `BambuStudio.conf` (включено 2026-09-17, иначе каждый `open` плодит окно — Дима путался в трёх), файл на холодный старт подвешивает Studio без окна. Рецепт целиком — скилл `print-model`, шаг 6. Если в окне уже открыт проект, `open` даёт диалог «Drop project file» (Open as project → OK) и затем «сохранить изменения?» (No — исходник с MakerWorld не трогаем); поверх уже нарезанного файла новый открывается без вопросов. Отправку («печатай») делаю кликами UIDrive: Print plate → в диалоге Send print job, если поле принтера пустое — кнопка обновления рядом с ним → Send; успех — `bbl_printer.py status` показывает PREPARE с новым файлом (2026-09-18). Признаки приёма приходят по очереди и первые минуты врут (20.09): сперва меняется `file`, а `layer`/`remaining` ещё от прошлой задачи, потом PREPARE, и только через ~3 мин RUNNING с правильным числом слоёв — **подтверждать по числу слоёв своей нарезки**, не по имени файла. Вкладка Device в Studio в это время показывает карточку прошлой печати — это кэш, не источник правды. Стол перед отправкой камерой **не проверять** и не спрашивать — свободен ли он и стоит ли пластина, решает Дима (2026-09-21, попросил убрать); камера (`bbl_printer.py camera`) — только по его просьбе, при открытой вкладке Device отдаёт `No frame available`. Если `pgrep` находит Studio, а `winctl windows` её не показывает, сперва `winctl front <pid>`: чаще окно просто свёрнуто, а не подвисло.
- `tools/gcode_layers.py` — по слоям из нарезанного G-code: время слоя, объекты, расход, вентилятор. `tools/gcode_features.py` — что и где печатается по типам фич (мосты и их пролёт, нависания, gap fill и доля крошечных сегментов, крыша поддержек) — основа прогноза дефектов в скилле `print-model`. `tools/gcode_airtravel.py` — переезды сопла через воздух внутри детали (нитки в окнах и каналах свистков, направляющих; `reduce_crossing_wall` окна не обходит), проверка 16.
- Автосейв живёт только пока проект открыт — всё, что понадобится позже, сразу копировать в `prints/`.
- `tools/bbs_resolve.py <filament|process|machine> "<имя>" [ключи]` — полный пресет с раскрытым `inherits`; файлы в `user/` хранят только overrides. **Ловушка:** для машин Bambu резолвер не даёт настоящих `*_gcode` — Studio 2.x их в системных JSON не хранит, и цепочка проваливается в заглушку `fdm_machine_common.json` (Ender-стиль, `M109 S205`, продувка за стол). Настоящие блоки — только из проекта, сохранённого Studio: снимок в `profiles/baseline/machine-gcode-A1mini.json`, `retarget` берёт оттуда. Утка 16.09 и первая коробка 17.09 ушли на 205 °C именно так. Перед отдачей в печать — `M1002` в G-code должен встречаться сотни раз; одиночный **отступом** `M109 S205 ; drop nozzle temp…` внутри блока смены филамента — законный кусок Bambu-макроса (есть в каждой нашей печати), заглушка Ender-стиля — это `M109 S205` без отступа при почти нулевом `M1002`.
- Глобально активные пресеты и тип стола — `~/Library/Application Support/BambuStudio/BambuStudio.conf` (JSON, ключи `presets.*`, `app.curr_bed_type`). Читать по ключам: в файле лежит `access_code` принтера.
- `tools/UIDrive.app` — клики/клавиши в Studio: `open -W --stdout out.txt -a tools/UIDrive.app --args click X Y | key 36 | type …` (разрешение Accessibility выдано 2026-09-16; **бинарник не пересобирать** — ad-hoc подпись, TCC привязан к хэшу). Рецепт клика по кнопке: `winctl front <pid>` → `winctl windows <pid>` даёт x y w h окна в поинтах → скриншот окна без тени (`ScreenGrab --args -x -o -l <windowID>`), координата кнопки на снимке ÷ 2 (Retina) + x/y окна → `click`. После клика — снова скриншот, убедиться. **Клавиатурный ввод (`type`/`key`) — только когда Дима явно не за Маком**: события идут в активное окно, и если он в этот момент печатает в Telegram, текст и Enter улетят туда (случай 2026-09-16). Меню Studio через клавиатуру не водить; скриншот через ScreenGrab закрывает открытые меню (перехват фокуса). Кадр с камеры принтера — `tools/bbl_printer.py camera out.jpg`.
- `tools/bbs_screenshot.sh` — скриншот экрана через `tools/ScreenGrab.app` (обёртка над screencapture: macOS даёт «Запись экрана» только .app-бандлам); один раз включить ScreenGrab в Системных настройках.
- Менять настройки: вариант проекта (`bbs_project.py variant --set`), а не инструкции по UI; постоянные изменения — JSON-пресетом в `profiles/user/` через Import Configs в Studio. Файлы в `user/` под запущенной Studio перезаписывает облачная синхронизация.
- Слайсинг без UI для проверки: `/Applications/BambuStudio.app/Contents/MacOS/BambuStudio --help`.
- Принтер по LAN: `tools/bbl_printer.py status|upload|print|stop|camera` (IP/serial в `.printer.json`, не в git; access code скрипт читает **в процессе** из `BambuStudio.conf` → `access_code[serial]` и никогда не печатает — в чат/репо он не попадает). Статус, заливка по FTPS и `system.ledctrl` работают; **все команды семейства `print` (`project_file`, `gcode_line`, `print_speed`) прошивка 01.08.01 отвечает `err_code 84033543` — авторизация сторонних клиентов, нужен Developer Mode на экране принтера** (2026-09-16). Ловушка: `start_print` при этом печатает `-> True` (библиотека рапортует об отправке, не о приёме) — судить только по `status` через 10–20 с: файл и слой не сменились, сопло холодное → команда отвергнута. То же с `stop`/`resume`. Без него удалённый старт — только через Bambu Handy с телефона: файл уже лежит на SD-карте.
- Калибровочные столы без мастера Studio: `tools/bbs_calib.py flow1|flow2|temp|speed` (логика 1:1 из CalibUtils.cpp), затем CLI-нарезка → `.gcode.3mf` → принтер. `temp` вырезает нужные блоки из 350-мм башни мастера (`tools/mesh_cut.py`, trimesh через uv; подписи STL 350 °C снизу → 180 сверху). `speed-ramp` переписывает подачу в G-code — верхний поток ≤ 26 мм³/с: Studio молча не грузит gcode.3mf с расходом выше ~26–28 мм³/с независимо от подачи (пустой Preview, серая Print plate; 4 → 30 и 20 → 40 на толстой линии не открылись, 4 → 26 открылся, 2026-09-19); выше — только `bbl_printer.py upload` на SD и старт с экрана принтера.

## Fusion

**Pattern on Path с типом Features — ловушка.** Каждый экземпляр заново выполняет всю цепочку выбранных фич и заново сшивает булевы операции; много фич × много экземпляров = память растёт как произведение. 19.09 Fusion на этом занял 89 ГБ при 16 ГБ RAM, своп забит, час «расчёта» был разрастанием памяти, а не работой — такое не досчитывается, только падает. Диагностика в одну команду: `ps -axo pid,%cpu,%mem,rss,command | grep 'Autodesk Fusion'` и `top -l 2 -s 20 -pid <pid> -stats pid,cpu,mem` — растущая на гигабайты память при 100 %+ CPU значит «убивать, не ждать». Снимок восстановления лежит в `~/Library/Application Support/Autodesk/Autodesk Fusion 360/<id>/CrashRecovery/` (имя документа и время — в `AutoSavedFileList.xml`, UTF-16), Fusion предложит его при следующем запуске. **Правильно:** повторяемый узел — отдельный компонент, паттерн по типу **Components/Bodies**, один Combine → Join в конце; Compute Option — Optimized; тяжёлую операцию держать в конце дерева и подавлять (Suppress) на время правок выше, либо откатывать маркер таймлайна ниже неё; перед тяжёлой операцией — сохранить версию.

**Part-документ не пускает второй компонент — ловушка Snap Generator и любого аддина.** Fusion 2705 работает по модели Parts & Assemblies: у документа есть design intent — Part / Assembly / **Hybrid** (`Design.designIntent`, 0/1/2). В **Part** `rootComponent.occurrences.addNewComponent()` падает с `RuntimeError: 3 : Failed to create component: Part Design documents can only contain one component`, и на этом ломается любой аддин, создающий компонент (Snap Generator — всегда, настройку убрали в 0.4.0, issue #19). В **Hybrid** тела в корне и компоненты уживаются — это поведение Fusion до 2026. Дефолт уже правильный: обычный новый документ создаётся Hybrid, ловушку даёт только пункт **New Part Design** в меню New — его не выбирать (ADR-0005). Диагностика: `des.isModelingInAssemblyEnabled` отвечает `Modeling in assembly API is only applicable to assembly designs` → документ не Assembly; точное значение — `des.designIntent`. Починить существующий Part: `des.designIntent = adsk.fusion.DesignIntentTypes.HybridDesignIntentType` (Part → Hybrid поддерживается, проверено 20.09) — команды в UI для этого нет, есть только обход `Add To Assembly` (`NewAssemblyFromPartCommand`). Выключателя у модели Parts & Assemblies нет: `NotifyPartAssemblyWorkflow` в `NGlobalOptions.xml` — флаг уведомления, не переключатель.

`tools/fmcp.py` — нативный MCP Fusion (127.0.0.1:27182, живёт пока Fusion запущен). `fusion_mcp_execute` с `featureType=script`, `object={script, readOnly}`; скрипт обязан определять `run(_context)`. Чтение (timeline, ThreadFeature.threadInfo, bRepBodies) — с `readOnly: true`, можно без спроса; шум `[MCP] Bind failed … 9876` в ответе — от add-in'а Faust, игнорировать.
